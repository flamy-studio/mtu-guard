# Архитектура MTU Guard 0.3

## Контекст

Сервис не является VPN-клиентом. Он исправляет наблюдавшийся на Windows AmneziaVPN 5.1.0.6 MTU 1376 при требовании WRE IPv4 MTU 1280. На устройствах без адаптера не выполняет операций с сетью.

## Топология процесса

```text
Windows SCM (Automatic / LocalSystem)
  └─ withen-mtu-guard.exe service
       ├─ RegisterServiceControlHandler (STOP/SHUTDOWN)
       └─ Worker
            ├─ NotifyIpInterfaceChange(AF_INET)
            ├─ GetIfTable2 -> разрешённое имя + Up + !hardware
            ├─ GetIpInterfaceEntry(AF_INET) -> единственный кандидат
            ├─ если !=1280: повторить выбор/чтение, сверить LUID
            ├─ SetIpInterfaceEntry -> новый выбор/чтение для verify
            └─ резервный опрос каждые 30 с
```

## Контракт Win32 API

1. `NotifyIpInterfaceChange(AF_INET, ...)` регистрируется **до** первого опроса. Microsoft документирует, что callback получает неполную MIB-строку; обработчик не читает её поля и не меняет интерфейс, а лишь посылает сигнал worker. Callback может приходить во время создания/удаления адаптера.
2. По сигналу worker объединяет события в фиксированном окне 400 мс, затем заново перечисляет интерфейсы через `GetIfTable2`, использует выравненную таблицу `MIB_IF_TABLE2.Table` (не смещение `+4`), освобождает память `FreeMibTable`. Окно не продлевается при новых событиях; STOP прерывает ожидание.
3. Политика допускает `AmneziaVPN` и `AmneziaVPN N`, N = 1..4294967295, ASCII-цифры без знака/ведущих нулей, регистр базы не важен. Нужны `IfOperStatusUp`, отсутствие HardwareInterface и строка IPv4. Из таблицы копируются alias, LUID, индекс, состояние, описание и тип. Старые неактивные экземпляры пропускаются. Подходящих кандидатов 0 — WAITING, 1 — выбор по его LUID, 2+ — AMBIGUOUS без записи. Базовое имя и номер не получают приоритета. См. [NET-002](NET-002.md).
4. `InitializeIpInterfaceEntry` -> `Family=AF_INET` -> `InterfaceLuid` -> `GetIpInterfaceEntry`. Проверяются семейство и LUID возвращённой строки. Только отсутствие строки превращается в отсутствие кандидата; другая ошибка API потенциального кандидата прекращает весь выбор. Перед записью повторяются полный выбор и чтение, требуется тот же LUID. Если MTU уже исправлен другим процессом, повторной записи нет. Свежая полная структура сохраняется; изменяются `NlMtu=1280`, обязательное для IPv4 `SitePrefixLength=0` и `InterfaceIndex=0` для обращения только по LUID.
5. `SetIpInterfaceEntry`, затем новый выбор и чтение через 350 мс. Успешная коррекция требует того же LUID и MTU 1280. Если интерфейс исчез/заменён, результат WAITING; неоднозначность, ошибка API или неверное значение — FAIL. Между последней проверкой и Set остаётся неатомарное окно гонки.
6. Очередь вмещает один ожидающий сигнал; повторные сетевые события объединяются. Нет накопления задержки 16 × 400 мс. Резервный опрос обеспечивает повторную сверку; уведомление от самого Set не создаёт цикл записи, поскольку при 1280 запись пропускается.
7. Остановка через SCM выставляет атомарный флаг и пытается отправить Stop без ожидания свободного места в очереди. Worker проверяет флаг перед каждым проходом, сообщает StopPending и снимает регистрацию через `CancelMibChangeNotify2` **вне** контекста callback. При ошибке отмены контекст сохраняется до завершения процесса, чтобы последующий callback не обратился к освобождённой памяти. Затем сообщается Stopped.

Внутренний цикл не создаёт внешних сокетов, не запускает оболочки и не нуждается в файлах настроек.

## Почему Windows Service, а не Scheduled Task

При появлении адаптера после запуска приложения без входа пользователя необходим почти немедленный callback и постоянное ожидание без повторных запусков с UAC. Служба подходит по жизненному циклу и не должна открывать окно или UI-сеанс. Альтернатива Task Scheduler с периодическими задачами не даёт такой же реакции на динамические изменения интерфейса.

## Ограничение гонок

`SetIpInterfaceEntry` может конфликтовать по времени с инициализацией интерфейса AmneziaVPN; обработка событий откладывается на 400 мс и повторяется при изменениях или через 30 с. Бесконечно и часто переписывать MTU запрещено: при верном значении нет системного вызова записи. При повторном появлении интерфейса используется новая запись и LUID.

## Наблюдаемость

Статус и лог сохраняют фактический alias, включая регистр и суффикс, описание/тип устройства. В CLI WAITING диагностика показывает найденные Amnezia-имена, Up, hardware и наличие запрошенной IPv4-строки. Для исключённых до чтения кандидатов IPv4 помечается `not-queried`. Сборщик JSONL использует фактическое имя; при WAITING/FAIL поля цели null, исходный текст/код сохраняются и наблюдение продолжается.

Никаких метрик в интернет. Локальный лог `%ProgramData%\WITHEN\MTU Guard\guard.log` (до 512 КиБ, 1 резервная копия) содержит `unix_ms`, LUID, ifIndex, MTU, `correction_ms`. Последнее — время от начала прохода с обнаружением неверного MTU до проверки результата, а не от рождения адаптера. LUID входит в сравнение состояний, поэтому пересозданный интерфейс логируется даже при уже верном MTU. CLI `status` и `check` показывают идентификаторы; при WAITING предлагаются только возможные Amnezia-alias. Адреса, пароли и параметры VPN не пишутся.

Служба ожидает системные события и просыпается раз в 30 секунд при их отсутствии; это малая ожидаемая нагрузка, а не буквальный «нулевой CPU». `collect-evidence.ps1` отдельно измеряет CPU процесса службы по разности накопленного времени; диагностические процессы в это измерение не входят.

## Windows 10/11 совместимость

Чистые правила находятся в `src/policy.rs`. `InterfaceApi` отделяет вызовы ОС от того же пути выбора/коррекции `apply`; единственный runtime backend — `NativeInterfaces`. Тестовый backend в `src/win/tests.rs` задаёт последовательные снимки/ошибки и фиксирует записи без изменения реальной сети. Проверяются гонки, ошибки, сохранение полей и верификация; модель не заменяет полевой тест драйвера.

Все используемые IP Helper функции поддерживаются как минимум со времён Windows Vista. Проект компилируется как нативный MSVC x64 и использует штатный SCM. Автоматический режим 0.3.0 — Verified на Windows 11 x64 (два ПК) и Windows 10 x64 build 19045: [сводное решение](FIELD_ACCEPTANCE_SUMMARY_2026-11-23.md). Windows 10 также прошла проверку WAITING/возврата адаптера и длительной работы одного процесса. Числовые имена, чистые ОС и другие непроверенные конфигурации учитываются отдельно; декларация API-совместимости не заменяет E2E.
