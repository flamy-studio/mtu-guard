# MTU Guard 0.3.0 — отчёт полевой приёмки Windows 11

**Дата:** 22 ноября 2026 г.\
**Проект:** MTU Guard / WITHEN MTU Guard\
**Версия:** 0.3.0, Windows x64, автоматический режим (Windows Service)\
**Разработчик и издатель:** [Flamy Studio](https://flamy.studio)\
**Заказчик:** [Withen Network](https://withen.pro)\
**Лицензия:** Apache-2.0\
**Основание:** переданные участниками консольные журналы, скриншоты и результаты практических проверок двух компьютеров с Windows 11.\
**Тип проверки:** пользовательская полевая приёмка (не сертификация Microsoft и не независимая лабораторная проверка).

## 1. Результат и матрица совместимости

**Решение по выпуску:** **Windows 11 x64 — VERIFIED / PASS** для основного функционала автоматической службы MTU Guard 0.3.0 в проверенных условиях. **Windows 10 x64 — EXPERIMENTAL**, поскольку на момент отчёта полевые проверки ещё не проведены.

| Платформа / компонент | Статус | Обоснование |
|---|---|---|
| Windows 11 x64 — автоматическая служба | **VERIFIED** | Два реальных ПК, установка, запуск, обнаружение AmneziaVPN, восстановление MTU, перезапуск VPN, перезагрузка ОС |
| Windows 10 x64 — автоматическая служба | **EXPERIMENTAL** | Поддержка предусмотрена архитектурой и требованиями проекта, но реальные испытания Windows 10 не завершены |
| Ручная утилита PowerShell / CMD | **TEST CANDIDATE** | Интегрирована в репозиторий, ранее выполнялись локальные проверки; отдельной полноценной пользовательской приёмки этого пакета в приведённых полевых логах нет |
| Windows ARM64 / 32-bit | **NOT SUPPORTED BY THIS PACKAGE** | Проверенный релизный бинарник рассчитан на Windows x64 |

**Важно:** VERIFIED означает, что *основной сценарий* версии 0.3.0 подтвердился на двух Windows 11. Это не означает испытание всех конфигураций Windows 11, числовых алиасов, совместной работы с любыми VPN или отсутствие всех возможных дефектов.

## 2. Проверенная конфигурация

- AmneziaVPN, подключение к `WITHEN_HUB`, адаптер с именем `AmneziaVPN` и описанием `WireGuard Tunnel` (тип интерфейса 53).
- Целевой параметр: **IPv4 MTU = 1280**; специально воспроизводимое ошибочное значение: **1376**.
- Служба Windows SCM: `WithenMtuGuard`, тип `WIN32_OWN_PROCESS`, состояние `RUNNING`.
- WRE Exit для подтверждения зарубежного маршрута: `45.80.228.141`.
- Проверка HTTPS: `Invoke-WebRequest https://1.1.1.1/cdn-cgi/trace` в Windows PowerShell 5.1.
- Испытания выполнялись с разрешения пользователей на их собственных машинах; исходные ключи и конфигурации VPN не собирались.

## 3. Подробные результаты

### Сценарий A — основная Windows 11 разработчика

| ID | Действие / проверка | Результат |
|---|---|---|
| W11-A01 | До установки служба отсутствовала: `sc.exe query WithenMtuGuard` возвращала `1060` | PASS |
| W11-A02 | На активном `AmneziaVPN` вручную задано `MTU=1376`; значение подтверждено `netsh` | PASS |
| W11-A03 | После `install.cmd` служба зарегистрирована и `RUNNING`; MTU автоматически восстановлен до `1280` | PASS |
| W11-A04 | При выключенном split tunneling дефолтный IPv4-маршрут выбран через `AmneziaVPN` (метрика интерфейса 5) | PASS |
| W11-A05 | PowerShell HTTPS-запрос через WRE завершился; Cloudflare показал `ip=45.80.228.141` | PASS |
| W11-A06 | Split tunneling включён и выключен; после обоих переходов служба `RUNNING`, MTU `1280` | PASS |
| W11-A07 | AmneziaVPN полностью завершена (включая процессы) и запущена снова; статус `PASS`, MTU `1280` | PASS |
| W11-A08 | При работающей службе вручную задан `1376`; мгновенный `status.cmd` показал `WARN`, последующий `netsh` подтвердил автоматический возврат `1280` | PASS |
| W11-A09 | После перезагрузки Windows служба `RUNNING`; `status.cmd` и `netsh` показывают `1280` | PASS |
| W11-A10 | Скриншот диспетчера задач в простое: CPU 0%, память около 0,7 МБ | OBSERVED (моментальный снимок) |

**Нюанс W11-A08:** промежуточный `WARN` является корректным результатом диагностики, успевшей прочитать MTU до асинхронного исправления. Дальнейшее значение `1280` подтверждено независимо через `netsh`. Нельзя интерпретировать такой кратковременный `WARN` как отказ службы.

**Нюанс W11-A06:** LUID `0x0035008000000000` и `ifIndex=2` в трёх проверках совпали. Тест подтверждает корректное состояние после смены режима; не доказывает, что каждый переход породил новый уникальный сетевой интерфейс и обязательно установил MTU 1376.

### Сценарий B — второй компьютер Windows 11 (`tofushka`)

| ID | Действие / проверка | Результат |
|---|---|---|
| W11-B01 | До установки MTU Guard служба отсутствовала (SCM `1060`) | PASS |
| W11-B02 | Адаптер `AmneziaVPN` обнаружен; ручная смена `1280 → 1376` подтверждена | PASS |
| W11-B03 | Затем MTU вернулся в `1280` ещё **до установки службы** | OBSERVED — не приписывать Guard |
| W11-B04 | Позже служба установлена и запущена (`RUNNING`); адаптер исчезал и появлялся при управлении VPN | PASS |
| W11-B05 | После появления адаптера MTU `1280`; служба `RUNNING` | PASS |
| W11-B06 | После перезагрузки Windows служба `RUNNING`, MTU `1280` | PASS |
| W11-B07 | При уже работающей службе принудительно задано `1376`; `netsh` подтвердил `1376`, затем `1280` без повторной команды изменения | PASS — автоматическое восстановление наблюдалось |
| W11-B08 | `status.cmd` показал `[PASS] AmneziaVPN IPv4 MTU = 1280`, `ifIndex=27`, описание `WireGuard Tunnel`, type=53 | PASS |
| W11-B09 | HTTPS к Cloudflare вернул `ip=45.80.228.141` | PASS — запрос был выполнен **до установки Guard**; не является отдельным post-install HTTPS-тестом |

**Атрибуция исправления:** в W11-B07 после `1376` произошло автоматическое восстановление во время работы Guard. Однако W11-B03 показывает, что AmneziaVPN на этой машине иногда самостоятельно возвращает `1280`. Для строгого доказательства происхождения *конкретной* записи B07 нужен журнал Guard с событием коррекции. Прямое исправление действующей службой на основной Windows 11 уже подтверждено последовательностью W11-A02/A03 и W11-A08.

### Нагрузка и влияние на систему

На основном ПК в диспетчере задач был зафиксирован показатель около **0% CPU и 0,7 МБ памяти** в простое. Длительный профилировочный тест CPU/RAM в приведённых полевых журналах отсутствует; утверждение `Zero CPU` или точный среднесуточный расход ресурсов **не подтверждены**. Изменения MTU выполняются по необходимости, а не на каждом пакете.

Изменений Ethernet MTU не наблюдалось: он оставался `1500`, в то время как `AmneziaVPN` восстанавливался до `1280`.

## 4. Особенности и наблюдения

1. **Раздельное туннелирование влияет на IP-контроль маршрута.** При включённом split tunneling внешний IP теста может быть российским, поскольку PowerShell идёт напрямую через Ethernet. При выключенном split tunneling на основном ПК проверены VPN default route и иностранный IP `45.80.228.141`.
2. **Появление/исчезновение адаптера штатно.** При остановке AmneziaVPN интерфейс может отсутствовать. Это соответствует состоянию `WAITING`, а не повреждению Windows или отказу службы.
3. **Windows Defender блокировал диагностический `curl.exe`.** Локальное обнаружение `!#SLF:CMD_HSTR:ClickFix.ML.J` относилось к командной строке `C:\Windows\System32\curl.exe`. Ещё одно обнаружение `Behavior:Win32/PFAppMultiStepRem.A` предшествовало полевому тесту. В представленных данных **нет доказательства**, что блокировался EXE MTU Guard. Защитные механизмы не отключались; HTTPS проверялся штатным PowerShell. Это наблюдение **не следует объявлять доказанным false positive**.
4. **Имя интерфейса.** В реальных испытаниях использован `AmneziaVPN` без числа. Поддержка `AmneziaVPN N` проверялась модельными тестами репозитория, но ещё не подтверждена на естественно созданном числовом адаптере.
5. **Перезагрузка.** Подтверждён штатный reboot двух Windows 11. Отдельное испытание после полного выключения питания и холодного запуска не выделялось.
6. **Цифровая подпись.** Предоставленный тестовый EXE не подписан Authenticode; это не было препятствием в этих двух испытаниях, но остаётся фактором публичного распространения.

## 5. Оставшиеся проверки — не блокируют статус VERIFIED для проверенного Windows 11-сценария

- Windows 10 x64 на ПК без сборочных инструментов, включая естественный `MTU=1376` и восстановление после перезагрузки: **EXPERIMENTAL / PENDING**.
- Числовой интерфейс `AmneziaVPN 1`/`2` и безопасный отказ при двух одновременно подходящих активных интерфейсах: **PENDING FIELD TEST** (модельная логика уже проверялась).
- Отдельное практическое тестирование ручного пакета `manual-mtu.cmd`/`manual-check.cmd` на внешней системе: **PENDING FIELD TEST**.
- Часовая телеметрия CPU/RAM при обычной эксплуатации: **PENDING**.
- Чистая Windows 11 без SDK/Rust/VC++ Redistributable: **PENDING**; статический анализ импортов EXE и тесты разработчика не равны чистой машине.
- Полная подпись Authenticode для публичных выпусков: **NOT SIGNED**.

## 6. Решение по статусам репозитория

Предлагается использовать следующие формулировки:

- **Windows 11 x64 — Verified (field-tested).** Основная служба MTU Guard 0.3.0 проверена на двух реальных ПК: исправление IPv4 MTU `1376 → 1280`, автозапуск службы, переподключения AmneziaVPN, переключение split tunneling, перезагрузка и доступ через WRE после исправления.
- **Windows 10 x64 — Experimental.** Совместимость заложена в реализацию, но реальные полевые испытания на Windows 10 ещё не завершены. Использовать как тестовый релиз с возможностью передать диагностический отчёт.
- **Manual mode — Test candidate.** Ручной режим распространяется отдельно и ещё не получил такой же объём полевой приёмки, как Windows Service.

**Решение:** разрешить тестовое распространение автоматического пакета 0.3.0 для Windows 11 x64 с отметкой Verified. Для Windows 10 x64 оставить статус Experimental до отдельного пользовательского испытания. Это решение касается *проверенной версии 0.3.0*, а не любых будущих сборок после внесения изменений.
